# Blog Content Service

A Go REST API for blog content with role-based access, soft delete, CSV export, and
**unique daily view counting** (one view per blog + client IP + UTC day). PostgreSQL is
the source of truth, while Redis caches authenticated actors and committed view markers.

- Go, Gin, PostgreSQL 18, Redis 8, pgx/v5, Goose migrations, hand-written SQL, and
  `log/slog` JSON
- Hexagonal layout: `transport/http` → `app` → `domain` ←
  `adapter/{postgres,redis}`
- The view counter is protected by a PostgreSQL primary key rather than process memory,
  so it remains correct across multiple service instances
- CORS allows calls from any origin; preflight requests are handled before authentication
  and application handlers

See [ARCHITECTURE.md](ARCHITECTURE.md) for the design and [openapi.yaml](openapi.yaml)
for the complete API specification.

## Quick start

Docker with Compose is required.

```bash
docker compose up --build
```

This starts PostgreSQL, Redis, migrations, the API at
[http://localhost:8080](http://localhost:8080), Swagger UI at
[http://localhost:8081](http://localhost:8081), and RedisInsight at
[http://localhost:5540](http://localhost:5540).

```bash
curl localhost:8080/healthz     # {"status":"ok"}
curl localhost:8080/readyz      # {"status":"ready"}; returns 503 if PostgreSQL is unreachable
```

Stop the stack with `docker compose down`. Add `-v` to delete the database volume too.

### Run the API outside Docker

```bash
cp .env.example .env            # edit values if needed
docker compose up -d postgres redis migrate
make run                        # loads .env, then runs go run ./cmd/api
```

## Configuration

Environment variables are documented below; see [.env.example](.env.example).

| Variable | Default | Description |
|---|---|---|
| `DATABASE_URL` | – (required) | PostgreSQL connection string |
| `HTTP_ADDR` | `:8080` | HTTP listen address |
| `TRUSTED_PROXIES` | empty | Comma-separated CIDRs of trusted reverse proxies; an empty value means forwarded headers are never trusted |
| `LOG_LEVEL` | `info` | `debug`, `info`, `warn`, or `error` |
| `SHUTDOWN_TIMEOUT` | `15s` | Graceful shutdown deadline |
| `DB_MAX_CONNS` | `20` | pgx connection pool size |
| `REDIS_ADDR` | empty (disabled) | Redis address, for example `localhost:6379` |
| `REDIS_PASSWORD` | empty | Redis password |
| `REDIS_DB` | `0` | Redis logical database |
| `REDIS_ACTOR_TTL` | `5m` | TTL for successful actor lookups |
| `REDIS_VIEW_TTL` | `48h` | TTL for committed unique-view markers |

Redis is a derived cache, not the source of truth. Actor cache misses and failures fall
back to PostgreSQL. The view Lua script checks only markers written after PostgreSQL
commits; Redis misses and failures execute the original atomic PostgreSQL statement.

> When running behind Nginx or a load balancer, set `TRUSTED_PROXIES` to its address
> range. Otherwise every visitor appears to have the proxy's IP and views are
> under-counted.

## Mock authentication

There is no login endpoint. Send `X-User-ID: <uuid>` for a user created by the seed
migration:

- No header → **Anonymous**, which may read blogs.
- A malformed or unknown ID → `401`.
- The role always comes from the database, never from the client.

The migration creates one user per role. IDs are generated by the database, so query
them before making authenticated requests:

```bash
docker exec postgres psql -U blog -d blog -c "select id, name, role from users order by role"
```

| Role | Read | Create | Update | Delete | CSV export |
|---|:-:|:-:|:-:|:-:|:-:|
| Admin | ✓ | ✓ | ✓ | ✓ | ✓ |
| Editor | ✓ | ✓ | ✓ | | |
| Reader | ✓ | | | | |
| Reporter | ✓ | | | | ✓ |
| Anonymous | ✓ | | | | |

An anonymous caller without a required permission receives `401`; an authenticated
caller without it receives `403`.

## API

The base path is `/api/v1`. See [openapi.yaml](openapi.yaml) for the full specification.

| Method | Path | Description |
|---|---|---|
| `GET` | `/blogs?page=1&limit=20` | List `id`, `title`, and `description`; never increments views |
| `GET` | `/blogs/{id}` | Read details and record the unique daily view |
| `POST` | `/blogs` | Create a blog (Editor, Admin) → `201` + `Location` |
| `PUT` | `/blogs/{id}` | Replace editable fields (Editor, Admin) |
| `DELETE` | `/blogs/{id}` | Soft delete a blog (Admin) → `204` |
| `GET` | `/reports/blogs` | Stream CSV (Admin, Reporter) |

```bash
EDITOR=<editor-id>; ADMIN=<admin-id>; REPORTER=<reporter-id>

# Create a blog
curl -i -X POST localhost:8080/api/v1/blogs \
  -H "X-User-ID: $EDITOR" -H 'Content-Type: application/json' \
  -d '{"title":"Hello","author":"Sky","content":"First post","description":"Introduction"}'

# List blogs, then read one; repeated reads from the same IP on the same UTC day stay at one view
curl 'localhost:8080/api/v1/blogs?page=1&limit=5'
curl localhost:8080/api/v1/blogs/<id>

# Update; optional version enables optimistic locking and returns 409 on mismatch
curl -X PUT localhost:8080/api/v1/blogs/<id> \
  -H "X-User-ID: $EDITOR" -H 'Content-Type: application/json' \
  -d '{"title":"Hello v2","author":"Sky","content":"Edited content","description":"","version":1}'

# Soft delete; the blog disappears from detail, list, and reports
curl -X DELETE localhost:8080/api/v1/blogs/<id> -H "X-User-ID: $ADMIN"

# Export CSV
curl localhost:8080/api/v1/reports/blogs -H "X-User-ID: $REPORTER" -o blogs.csv
```

Rules worth knowing:

- `page` must be at least 1. `limit` must be between 1 and 100 and defaults to 20.
  Out-of-range values return `400`; they are not clamped. List responses contain
  `has_next` rather than a total count.
- Request bodies require `Content-Type: application/json`, are limited to 1 MB (`413`),
  and reject unknown fields (`400`). Character limits are: title 1–255, author 1–100,
  content 1–100000, and description at most 500.
- Timestamps use RFC3339 in UTC.
- If PostgreSQL cannot record a view, the detail endpoint returns `503` instead of
  returning `200` and silently losing the view.

Every error uses the same envelope:

```json
{
  "error": {
    "code": "VALIDATION_FAILED",
    "message": "invalid request",
    "details": [
      {
        "field": "title",
        "message": "is required"
      }
    ],
    "request_id": "a80dba855a5f03ec"
  }
}
```

| Status | Code |
|---|---|
| 400 | `VALIDATION_FAILED`, `INVALID_JSON` |
| 401 | `UNAUTHENTICATED` |
| 403 | `FORBIDDEN` |
| 404 | `NOT_FOUND` |
| 405 | `METHOD_NOT_ALLOWED` |
| 409 | `VERSION_CONFLICT` |
| 413 | `PAYLOAD_TOO_LARGE` |
| 415 | `UNSUPPORTED_MEDIA_TYPE` |
| 500 / 503 | `INTERNAL_ERROR` / `SERVICE_UNAVAILABLE` |

## Testing

```bash
go test ./test/unit/...          # tests with in-memory repositories
go test ./test/integration/...   # tests against the running PostgreSQL instance
TEST_DATABASE_URL='postgres://user:pass@host/db?sslmode=disable' go test ./test/integration/...
go test ./...                    # both suites; integration tests require PostgreSQL
go test -race ./...              # both suites with the race detector
go vet ./...
```

- **Unit tests** in `test/unit` run the real services and router while replacing
  outbound adapters with in-memory fakes. Each endpoint covers successful responses,
  invalid input, and the permission matrix; CORS has a dedicated test.
- **Integration tests** in `test/integration` exercise all six APIs through the real
  PostgreSQL adapters. They try `TEST_DATABASE_URL`, then `DATABASE_URL`, then the
  default Compose database at `localhost:5432`. Tests never truncate tables and delete
  only blogs they created.

## Load testing and performance

Load tests require a local k6 installation. Each script defines its own stages and
thresholds:

| Script | Operation |
|---|---|
| `loadtest/k6/read_blogs.js` | `GET /api/v1/blogs` |
| `loadtest/k6/read_detail_blog.js` | `GET /api/v1/blogs/:id` |
| `loadtest/k6/create_blog.js` | `POST /api/v1/blogs` |
| `loadtest/k6/update_blog.js` | `PUT /api/v1/blogs/:id` |

Start the service, seed a deterministic dataset, and retrieve an Editor ID for create
and update requests:

```bash
docker compose up -d --build
make seed
EDITOR_ID="$(docker exec postgres psql -U blog -d blog -Atc \
  "SELECT id FROM users WHERE role = 'editor' ORDER BY id LIMIT 1")"
```

Run each script separately:

```bash
k6 run loadtest/k6/read_blogs.js
k6 run -e DETAIL_POOL=1 loadtest/k6/read_detail_blog.js
k6 run -e EDITOR_ID="$EDITOR_ID" loadtest/k6/create_blog.js
k6 run -e EDITOR_ID="$EDITOR_ID" -e ROWS=1000000 loadtest/k6/update_blog.js

# Run test with real-time web dashboard enabled (accessible at http://127.0.0.1:5665)
K6_WEB_DASHBOARD=true k6 run loadtest/k6/read_detail_blog.js
```

When the k6 Web Dashboard is enabled `(K6_WEB_DASHBOARD=true)`, open
[http://127.0.0.1:5665](http://127.0.0.1:5665). All scripts default to
`http://localhost:8080/api/v1`; set `-e BASE_URL=http://host:port/api/v1` to target a
different instance. `BLOG_ID=<uuid>` selects a specific blog for detail or update tests.
For random update selection, `ROWS` must not exceed the number of seeded rows.

The seed is additive and idempotent. `ROWS=10000 make seed` adds deterministic blogs
through `blog-10000` without deleting existing data. Use `docker compose down -v` to
reset the local database.
